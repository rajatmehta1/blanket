Architecture & Design v2.0

Complete technical reference for BlanketAudit's seven-tier pipeline, dual-layer analysis engine, and the design principles that govern every module.

What BlanketAudit Does

BlanketAudit is an AI-powered architecture governance platform. It accepts one or more Git repositories—hosted on GitHub, GitLab, Bitbucket, or stored locally—and produces a comprehensive audit report covering security vulnerabilities, compliance posture, architectural health, and code quality.

Multi-Repo

Scan multiple repositories in a single run. Cross-repo HTTP call detection links microservice boundaries automatically.

6 Languages

Tree-sitter AST parsing for Python, TypeScript/JS, Java, Go, Rust, and C#. Infrastructure files (Dockerfile, K8s YAML, Terraform, CI/CD) are also parsed.

4 Compliance Frameworks

HIPAA, SOC 2, PCI-DSS, and GDPR. Each finding is mapped to specific clauses. A compliance matrix shows pass/partial/fail per control.

4 Output Formats

PDF (dark-theme, WeasyPrint), interactive HTML, machine-readable JSON, and SARIF for IDE/GitHub integration.

Interfaces

CLI Typer + Rich Developer workstation, CI/CD pipelines
API FastAPI (async, Pydantic v2) Programmatic access, SaaS mode

6 Immutable Design Principles

These principles are non-negotiable. Every module, every pull request, every line of code must satisfy all six. They exist to prevent the failure modes that plague AI-based analysis tools: hallucinated findings, runaway costs, and non-reproducible results.

1. Dual-Layer Analysis

Static scanners produce CANDIDATES. AI agents apply contextual reasoning. Static ALWAYS runs first. AI NEVER runs alone.

Every finding begins life as a candidate from a deterministic tool (Semgrep, Gitleaks, OSV, AST queries). The AI layer then reasons about context—is this a true positive? What compliance controls does it violate? What is the blast radius? This two-phase approach means the system never hallucinates findings from thin air. 

# The dual-layer flow inside every agent:

# Phase 1: Static (deterministic, fast, no LLM)
semgrep_results  = run_semgrep(files, rules="p/security-audit")
gitleaks_results = run_gitleaks(repo_path)
osv_results      = run_osv_scanner(manifest_files)

# Phase 2: AI (contextual, LLM-powered, optional)
llm = get_llm_for_agent("security")
if llm:
    enriched = llm.invoke(prompt.format(
        candidates=semgrep_results,
        code_context=surrounding_code,
        call_chain=graph_analyzer.trace_to_entry(file, line)
    ))
else:
    # Graceful degradation: return static-only findings
    enriched = static_fallback(semgrep_results)

2. Graceful Degradation

One agent failure never kills a scan. If LLM API is unavailable, every agent falls back to static-only analysis.

The system is designed for partial failure. If the Anthropic API returns 503, the security agent still produces findings from Semgrep. If Neo4j is down, call graph analysis is skipped but the scan completes. If Milvus is unavailable, semantic search falls back to keyword matching. Every external dependency has an explicit fallback path. 

# Fallback hierarchy for each external dependency:

LLM Provider:
  anthropic/openai/groq  →  ollama (local)  →  none (static-only)

Knowledge Graph:
  Neo4j                  →  in-memory networkx DiGraph

Vector Database:
  Milvus                 →  in-memory FAISS  →  keyword search

Relational DB:
  PostgreSQL             →  SQLite (CLI mode)

# Circuit breaker pattern:
5 failures in 60s  →  OPEN (stop calling)  →  static fallback
After 120s         →  HALF-OPEN (try one call)
Success            →  CLOSED (resume normal)

3. Cost-Aware Execution

Every scan begins with a dry-run cost estimate. Token budgets are enforced per-agent with hard abort thresholds.

Before any LLM call, the system estimates total token usage and projected cost. The --dry-run flag shows this estimate without spending any tokens. During execution, each agent has a token budget (default 500K tokens). At 80% consumption, remaining files are demoted to static-only. At 100%, LLM calls stop entirely.

4. Reproducible Audits

Every scan records a ScanManifest. Past scans can be replayed deterministically.

The ScanManifest captures every variable that could affect output: policy YAML versions, prompt template hashes, LLM model IDs, static tool versions, and exact repo commit SHAs. Two runs with the same manifest produce identical results. This is critical for compliance audits where you must prove what was scanned and when.

5. Hallucination Guardrails (4 Gates)

4 validation gates prevent AI-generated findings from reaching the report without verification. NO finding enters the report without passing all 4 gates.

This is the most critical design principle. LLMs can hallucinate file paths, invent line numbers, fabricate compliance control IDs, and generate plausible-sounding but entirely fictional vulnerabilities. The 4-gate pipeline catches all of these.

6. Incremental Scanning

Subsequent scans analyze only changed files and their dependents. Content-hash keyed: SHA-256(file_content + policy_version).

After the first full scan, BlanketAudit caches results per file. On the next scan, it computes git diff against the cached commit, identifies changed files, then uses the file-level dependency graph to compute the reverse-dependency closure—all files that import a changed file also need re-analysis. Everything else reuses cached findings. 

# Incremental scan flow:

Scan N (full):
  patient_handler.py  SHA-256: a1b2c3...  → findings cached
  auth_middleware.py   SHA-256: d4e5f6...  → findings cached
  claim_service.py     SHA-256: 7a8b9c...  → findings cached

Scan N+1 (incremental):
  patient_handler.py  SHA-256: CHANGED     → re-analyze
  auth_middleware.py   SHA-256: d4e5f6...  → cache hit (unchanged)
  claim_service.py     imports patient_handler → re-analyze (dependent)

  Files analyzed: 2/3 (33% work saved)
  On large repos (1000+ files): typically 80-95% cache hit rate

Parses every source file using Tree-sitter, builds the file-level dependency graph (which file imports which file), extracts dependency manifests for CVE scanning, and indexes file metadata.

Tier 2.5: Entity Extraction & Call Graph

Deep AST walking extracts classes, methods, function calls, parameters, variables, and entry points. This data powers the method-level call graph—stored in Neo4j as (:Method)-[:CALLS_DIRECTLY]->(:Method) relationships.

Key distinction: The file-level dependency graph (Tier 2) answers "which files are related?" The method-level call graph (Tier 2.5) answers "which methods call which?" They are built separately, stored differently, and serve different purposes.

Tier 3: AI Orchestrator (LangGraph StateGraph)

The orchestrator is a LangGraph StateGraph that coordinates the entire pipeline. It triages files (no LLM), estimates cost, assembles batches, dispatches to agents in parallel, then merges results.

  .add_node("extract_entities",  extract_entities)
  .add_node("build_call_graph",  build_call_graph)

# File triage scoring (pure heuristics, no LLM):
score = (
    language_relevance(file)     # source > config > docs
  + file_type_weight(file)       # route handler > utility > test
  + recency_bonus(file)          # modified in last 30 days: +20
  + import_count(file, dep_graph)# high fanout = important
  + size_factor(file)            # larger files = more to analyze
)
# Tier assignment:
#   score > 60  → Tier 1 (full AI analysis)
#   30 - 60     → Tier 2 (static + light AI)
#   score < 30  → Tier 3 (static only, no LLM)

Tier 4: AI Analysis Agents (Parallel)

Four specialized agents run in parallel via LangGraph's Send API. Each follows the same pattern: run static tools first, feed candidates to the LLM, validate output through the 4-gate pipeline.

AgentStatic ToolsAI ReasoningModel Tier
Security Semgrep SAST + Gitleaks + OSV CVEs Blast radius, taint analysis, exploit assessment Standard (Sonnet)
Compliance AST queries + Milvus semantic search Control mapping, gap analysis, regulatory reasoning Higher (Opus/GPT-4)
Architecture Dependency graph + topological sort Layer violations, coupling assessment, pattern detection Standard (Sonnet)
Quality Complexity metrics + coverage parsing Refactoring recommendations, dead code assessment Standard (Sonnet) 
# Base agent pattern (all 4 agents follow this):
# Defined in codeaudit/agents/base_agent.py

class BaseAuditAgent:
    def analyze(self, context: AnalysisContext) -> list[AuditFinding]:
        # Step 1: Static analysis (ALWAYS runs)
        candidates = self.run_static_tools(context)

        # Step 2: AI enrichment (optional, may fail gracefully)
        llm = get_llm_for_agent(self.agent_name)
        if llm and self.token_budget.has_remaining():
            try:
                enriched = self.run_ai_analysis(llm, candidates, context)
            except Exception as e:
                log.warning("ai_fallback", agent=self.agent_name, error=str(e))
                enriched = self.static_fallback(candidates)
        else:
            enriched = self.static_fallback(candidates)

        # Step 3: Validate through 4 hallucination gates
        validated = self.validation_pipeline.run(enriched)

        return validated

All findings from the four agents are merged, deduplicated, scored, and assembled into the data structures that drive the report.

# Risk scoring formula:

# Per-category score (8 categories):
category_score = 100 - (critical_count * 25 + high_count * 10 + medium_count * 3 + low_count * 1)
category_score = max(0, min(100, category_score))  # Clamp [0, 100]

# 8 report categories:
#   Security, {Framework} Compliance (one per active framework),
#   Code Quality, Performance, Reliability, Infrastructure

# Weighted composite:
overall = (
    0.35 * security_score
  + 0.30 * avg(compliance_scores)
  + 0.15 * quality_score
  + 0.10 * performance_score
  + 0.10 * infra_score
)

# Grade thresholds:
#   A >= 85  |  B >= 70  |  C >= 50  |  D >= 30  |  F < 30

Data Flow: Raw Findings to Final Report

This section traces a single finding from its origin as a static tool candidate through AI enrichment, the 4 validation gates, deduplication, scoring, and final inclusion in the report. 


 ┌──────────────────────────────────────────────────────────────────────┐
 │                 DATA FLOW: FINDING LIFECYCLE                         │
 └──────────────────────────────────────────────────────────────────────┘

 1. STATIC TOOL DETECTION

    │  rule: python.lang.security.sqli          │

      - compliance_refs (HIPAA §164.312(a)(1), PCI-DSS Req 6.5.1)
      - fix_code (parameterized query replacement)
      - dollar_impact ("$50,000 — $1,900,000")
      - blast_radius (entry_points: 3, repos: 2)
      - call_chain (POST /api/patients → search() → execute_query())

    Check: services/patient_search.py exists in repo?  ✓
    Check: line 42 ≤ file length (387 lines)?          ✓

    Finding confidence: 0.92  (threshold: 0.70)

    Severity: critical

    2 agents agree → ✓ PASS → keep as critical

LLM Provider Abstraction

ALL LLM access in the entire codebase goes through the codeaudit/llm/ module. No other module may import provider SDKs directly. This is enforced at the code review level and is a non-negotiable boundary. 

# ✅ CORRECT — anywhere in the codebase:
from codeaudit.llm.provider import get_llm, get_llm_for_agent
from codeaudit.llm.embeddings import get_embeddings

llm = get_llm()                    # Returns BaseChatModel or None
llm = get_llm_for_agent("security")# Returns model configured for this agent
embeddings = get_embeddings()      # Returns Embeddings or None

# ❌ NEVER — anywhere outside codeaudit/llm/:
from anthropic import Anthropic     # FORBIDDEN
import openai                       # FORBIDDEN
from groq import Groq               # FORBIDDEN

Per-Agent Model Routing

Different agents have different capability requirements. The compliance agent needs higher-quality reasoning (regulatory nuance) and is routed to a more capable model. Other agents use the standard model to control costs.
