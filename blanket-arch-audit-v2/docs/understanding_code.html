Understanding the Code

A plain-English walkthrough of how BlanketAudit works, from the moment you run a scan to the final PDF report. No jargon walls — just the flow.

The Big Picture

BlanketAudit takes one or more code repositories as input and produces a detailed security, compliance, architecture, and quality report. The entire process is a 7-tier pipeline where each tier feeds the next:

You run a scan
  ↓
Clone / load repos          (Tier 1 — Connectors)
  ↓
Parse every file            (Tier 2 — Ingestion)
  ↓
Extract methods & calls    (Tier 2.5 — Entity Extraction)
  ↓
Decide what to analyze      (Tier 3 — Triage & Orchestration)
  ↓
Run 4 AI agents in parallel (Tier 4 — Analysis)
  ↓
Score, validate, merge      (Tier 5 — Aggregation)
  ↓
Generate report             (Tier 6 — Report)
  ↓
Deliver output              (Tier 7 — Delivery)

Let's walk through each step.

Step-by-Step Flow

Entry Points: CLI or API

You can kick off a scan two ways:

  • CLI — blanketaudit scan ./my-repo --domain healthcare --framework hipaa
    blanketaudit/cli/main.py
  • API — POST /api/v1/scan with repo URLs and options
    blanketaudit/api/app.py

Both paths end up calling the same orchestrator pipeline. The CLI is for local use; the API is for CI/CD or a web frontend.

↓

Tier 1: Source Connectors

The system needs code on disk to analyze. Connectors handle fetching it:

ConnectorWhat it doesFile
LocalReads a folder or extracts a zipconnectors/local_connector.py
GitHubClones via HTTPS with OAuth or PATconnectors/github_connector.py
GitLabClones via HTTPS with Project Access Tokenconnectors/gitlab_connector.py
BitbucketClones via HTTPS with App Passwordconnectors/bitbucket_connector.py

Every connector returns the same thing: a local filesystem path where the code lives. The rest of the pipeline doesn't care where the code came from.

Safety: Remote connectors block private IPs (SSRF protection) and enforce a 120-second clone timeout.

↓

Tier 2: Ingestion Engine

Now the system reads and indexes every file in the repo:

  1. File Indexer — Walks the directory tree, classifies each file (source, config, infra, test, docs), records language, line count, and computes a SHA-256 content hash.
    ingestion/file_indexer.py
  2. AST Parser — Uses Tree-sitter to parse source files into Abstract Syntax Trees. Supports Python, TypeScript/JS, Java, Go, Rust, C#.
    ingestion/ast_indexer.py
  3. Dependency Graph — Analyzes import/require statements to build a file-level graph: "which file imports which file." Fast, no deep AST walking needed.
    ingestion/dependency_graph.py
  4. Manifest Parser — Reads package.json, pom.xml, requirements.txt etc. to extract dependency lists for CVE scanning later.
    ingestion/manifest_parser.py
↓

Tier 2.5: Entity Extraction & Call Graph

This is where the system goes deeper than files — it maps out individual functions, classes, and who-calls-whom.

Extractors (one per language/tech) walk the AST and pull out:

  • Classes, methods, and their parameters
  • Function calls (which function calls which)
  • Entry points (API routes like @app.post("/api/patients"))
  • Imports and environment variable usage

ingestion/extractors/python_extractor.py, typescript_extractor.py, java_extractor.py, etc.

The Call Graph Builder then stitches all extracted calls into a method-level graph:

  • Each node = a specific function (e.g., patient-api::ClaimService.submit_claim())
  • Each edge = "this function calls that function"
  • Cross-repo edges match HTTP client calls to endpoint handlers

callgraph/static_builder.py — callgraph/cross_repo_matcher.py

Why two graphs? The file-level dependency graph (Step 3) is fast and answers "which files are related." The method-level call graph is more expensive and answers "which functions call which functions" — needed for blast radius and taint tracking.

↓

Tier 3: Triage (No AI — Pure Heuristics)

Not every file deserves the same level of analysis. The triage system scores each file 0–100 based on signals like:

  • Language relevance (Python source > markdown docs)
  • File type (route handler > utility > test)
  • Naming patterns (auth, payment, encrypt score higher)
  • Import count (more imports = architecturally important)
  • Recent git changes (modified in last 30 days = more relevant)

triage/file_scorer.py

Based on the score, each file gets a tier:

  • Tier 1 Score > 60 — Full AI analysis with all policy checks
  • Tier 2 Score 30–60 — Static tools + light AI summary
  • Tier 3 Score < 30 — Static tools only, no LLM calls

triage/tier_assigner.py

Files are then grouped into batches that fit within token limits (150K tokens max per batch), so the LLM never gets overwhelmed.
triage/batch_assembler.py

↓

Cost Estimation & Budget Check

Before spending any money on LLM calls, the system projects the total cost:

  • Counts tokens per file, per tier, per agent
  • Looks up pricing for the configured LLM provider/model
  • Returns a CostEstimate with total USD, per-agent breakdown, and a recommendation

orchestrator/cost_estimator.py

If this is a dry-run, the scan stops here and returns the estimate. Otherwise, if the projected cost exceeds the configured budget (max_scan_cost_usd, default $15), the scan aborts.

↓

Static Analysis (Deterministic, No AI)

Three tools run in parallel to produce candidate findings:

ToolWhat it findsFile
SemgrepCode vulnerabilities (SQL injection, XSS, etc.)agents/tools/semgrep_tool.py
GitleaksHardcoded secrets (API keys, passwords, tokens)agents/tools/gitleaks_tool.py
OSV-ScannerKnown CVEs in dependenciesagents/tools/osv_tool.py

These are deterministic — same code always produces the same results. They run regardless of whether an LLM is configured. Their output becomes input for the AI agents.

↓

Tier 4: Four AI Agents in Parallel

This is where the magic happens. Four specialized agents analyze the code simultaneously, each following the same pattern: static checks first, then AI reasoning on the candidates.

Security Agent

Takes Semgrep, Gitleaks, and OSV results. Uses AI to filter false positives, assess real-world exploitability, and compute blast radius.

agents/security_agent.py

Compliance Agent

Checks code against compliance frameworks (HIPAA, SOC2, PCI-DSS, GDPR). Uses semantic search (Milvus) to find relevant code patterns, then AI maps them to specific control clauses.

agents/compliance_agent.py

Architecture Agent

Analyzes the dependency and call graphs. Detects layer violations, circular dependencies, coupling issues, and single points of failure.

agents/architecture_agent.py

Quality Agent

Evaluates code quality: cyclomatic complexity, dead code, test coverage gaps, maintainability problems, and technical debt patterns.

agents/quality_agent.py

Every agent follows the template in agents/base_agent.py:

1. Run static checks          # deterministic, always runs
2. Feed candidates to LLM     # contextual AI reasoning
3. Validate LLM output         # parse into Pydantic models
4. Return findings             # or static-only if LLM fails

Key rule: If the LLM is unavailable or the budget runs out, every agent falls back to static-only analysis. One agent failing never kills the scan.

↓

Hallucination Guardrails (4 Gates)

AI can hallucinate — invent file paths, fabricate vulnerabilities, or exaggerate severity. Every AI-generated finding must pass through 4 validation gates before it reaches the report:

Gate 1: Schema Validation — Can the finding be parsed into a valid Pydantic model? Are compliance control IDs in the right format (e.g., §164.312 for HIPAA)?
validation/gate_schema.py
Gate 2: Evidence Verification — Does the file actually exist? Are the line numbers valid? Does the code snippet match what's really in the file (80% fuzzy match)?
validation/gate_evidence.py
Gate 3: Confidence Check — If the AI's confidence is below 0.7, the finding gets flagged as "REVIEW_NEEDED" instead of being stated as fact.
validation/gate_confidence.py
Gate 4: Corroboration — A "critical" severity finding from only one agent gets demoted to "high." True criticals need evidence from multiple agents.
validation/gate_corroboration.py

The gates run sequentially via validation/pipeline.py. Static tool findings (Semgrep, Gitleaks, OSV) skip gates 2–4 since they're deterministic.

↓

Tier 5: Finding Aggregation & Scoring

The validated findings are now assembled into a complete picture:

  1. Deduplicate — Same file + same line + same category = one finding (keep highest confidence).
    scoring/finding_merger.py
  2. Health Score — Calculate an overall 0–100 score across 8 categories. Formula: start at 100, subtract penalties (critical = −25, high = −10, medium = −3, low = −1). Grade: A ≥ 85, B ≥ 70, C ≥ 50, D ≥ 30, F < 30.
    scoring/risk_scorer.py
  3. Blast Radius — For each finding, compute how far it reaches: entry points affected, repos in the blast zone, estimated daily calls.
    scoring/blast_radius.py
  4. Call Chain Trace — Trace the path from API entry point → through the code → to the vulnerability.
    scoring/call_chain_tracer.py
  5. Dollar Impact — Estimate the financial risk of each finding (e.g., "$50,000 – $1,900,000").
    scoring/dollar_impact_estimator.py
  6. Compliance Matrix — Map findings to framework controls and set PASS/PARTIAL/FAIL for each clause.
    scoring/compliance_matrix_builder.py
  7. Remediation Roadmap — Group fixes into 30/60/90 day phases, prioritized by impact.
    scoring/remediation_planner.py
  8. Executive Summary — AI generates 2 paragraphs + a list of immediate action items.
    llm/prompts/executive_summary.py

All of this is orchestrated by scoring/report_assembler.py, which packages everything into a single AuditReport Pydantic model.

↓

Tier 6: Report Generation

The AuditReport model contains everything needed. It gets rendered into multiple formats:

PDF

Dark-themed, print-ready. WeasyPrint converts HTML → PDF with SVG charts, syntax-highlighted code, and page numbers.

report/pdf_generator.py

HTML

Interactive report with expandable finding cards. Jinja2 templates render 9 sections.

report/html_generator.py

JSON

Machine-readable export. Includes a CI/CD summary mode with just critical findings.

report/json_exporter.py

SARIF

Standard format for IDE integrations and GitHub code scanning alerts.

report/sarif_exporter.py

The 9 Report Sections

#SectionWhat's in it

2Executive Summary2 AI paragraphs + numbered urgent actions
3Score DashboardOverall gauge + 8 category bars with scores
4Critical FindingsExpandable cards with code, explanation, fix, call chain, blast radius

Templates live in report/templates/ (one per section).

↓

Tier 7: Output Delivery

The generated reports are delivered based on context:

  • CLI — Files saved to the local filesystem, summary printed to terminal
  • API — Results stored in DB, available via GET /api/v1/scan/{id}
  • CI/CD — JSON summary with exit code (0 = pass, 1 = critical findings found)
  • Scan history — Every scan is recorded in SQLite for trend tracking

How the LLM Layer Works

All LLM access goes through a single abstraction layer — the rest of the codebase never imports provider SDKs directly.

# Anywhere in the codebase:
from codeaudit.llm.provider import get_llm, get_llm_for_agent

llm = get_llm()                    # Returns a LangChain BaseChatModel
llm = get_llm_for_agent("compliance") # May return a more powerful model

llm/provider.py handles:

  • 6 providers: Anthropic, OpenAI, Ollama, Groq, Google, Azure
  • Per-agent model routing: Compliance gets a stronger model (e.g., Claude Opus), others get standard (e.g., Claude Sonnet)
  • Cost tracking: Every call is metered — tokens counted, USD tracked, budget enforced (llm/cost_tracker.py)
  • Circuit breaker: 5 failures in 60s = stop calling the LLM, fall back to static (llm/resilience.py)
  • Prompt injection defense: All code sent to the LLM is wrapped in <untrusted_code> tags with explicit warnings (llm/guardrails.py)

6 Design Principles

Every piece of code follows these rules:

  • 1. Dual-layer analysis — Static tools find candidates. AI applies reasoning. Static always runs first. AI never runs alone.
  • 2. Graceful degradation — If the LLM is down, every agent falls back to static-only. One failure never kills a scan.
  • 3. Cost-aware execution — Every scan starts with a cost estimate. Token budgets are enforced per-agent with hard abort thresholds.
  • 4. Reproducible audits — Every scan records a manifest with exact versions, commit SHAs, and config hashes. Scans can be replayed.
  • 5. Hallucination guardrails — 4 validation gates prevent AI-generated findings from reaching the report without verification.
  • 6. Incremental scanning — Subsequent scans only analyze changed files. Cache is keyed by SHA-256(content + policy_version).

The Orchestrator

The pipeline is built with LangGraph (a state machine framework). Each step is a "node" that reads from and writes to a shared AuditState.

orchestrator/pipeline.py — orchestrator/state.py

# Simplified pipeline flow:
ingest_repos → triage_files → estimate_cost
  → [budget check]
  → run_static_analysis
  → [4 agents in parallel]
  → validate_findings
  → score_and_prioritize
  → generate_report
  → record_manifest

If LangGraph is not available, a SimplePipeline fallback runs the same steps sequentially.
