Call Graph & AST Explained Deep Dive

How BlanketAudit uses Tree-sitter parsing, file-level dependency graphs, and method-level call graphs to power blast radius analysis, taint tracking, and cross-repo vulnerability detection.

What is a Call Graph?

A call graph is a directed graph where each node represents a function or method, and each edge represents a call from one function to another. If function A() calls function B(), there is an edge A → B. Call graphs answer the question: "If a vulnerability exists in function X, which entry points can reach it?"

Call graphs are the backbone of security analysis. Without them, you can find a vulnerability but cannot measure its real-world impact. With them, you know exactly how many API endpoints, users, and daily requests flow through the vulnerable code.

File-Level Dependency Graph vs. Method-Level Call Graph

BlanketAudit builds two separate graphs at different stages of the pipeline. They serve different purposes and are constructed differently:

File-Level Dependency Graph

Built in: Tier 2 (Ingestion)

Construction: Parse import / require / from statements. No deep AST walk needed.

Storage: NetworkX DiGraph in memory

Answers: "Which files are related?"

Used by:

  • Triage scorer (import count = importance)
  • Incremental scanner (reverse-dependency closure)
  • Architecture agent (coupling, layer violations)

Method-Level Call Graph

Built in: Tier 2.5 (Entity Extraction)

Construction: Full AST walk + symbol resolution + cross-file import mapping.

Storage: Neo4j as (:Method)-[:CALLS_DIRECTLY]->(:Method)

Answers: "Which methods call which methods?"

Used by:

  • Security agent (blast radius, taint paths)
  • Architecture agent (method coupling, dead code)
  • Scoring (blast radius multiplier on findings)

Why Both?

The dependency graph is fast (built during ingestion from import statements alone) and is used for quick triage decisions. The call graph is expensive (requires full AST walking with symbol resolution) but gives precise method-to-method edges needed for blast radius computation and taint tracking. They are complementary, not redundant.

Why It Matters for Security

  • Blast radius: Given a vulnerability at db.query(), reverse-BFS through the call graph finds every entry point that can trigger it, how many repos are affected, and estimated daily invocations.
  • Taint paths: Track untrusted user input from an HTTP parameter through method calls to a dangerous sink (SQL query, file write, shell exec). Each step in the chain is a CallChainStep.
  • Dead code: Methods with zero incoming edges in the call graph are unreachable. BlanketAudit reports these as dead code with total line counts.
  • Single points of failure: Methods on critical paths (entry point → data store) with no fallback or redundancy are flagged as SPOFs.

Sample Call Graph

Given a multi-file project, BlanketAudit resolves cross-file calls using the symbol table and import map to build a complete method-level call graph. Consider these four files: 

# routes.py
from services import PatientService

@app.get("/api/patients/search")
def get_patient_endpoint(query: str):
    return PatientService().search(query)

# services.py
from repositories import PatientRepo

class PatientService:
    def search(self, query: str):
        return PatientRepo().execute(query)

# repositories.py
from db import Database

class PatientRepo:
    def execute(self, query: str):
        return Database().query(f"SELECT * FROM patients WHERE name='{query}'")

# db.py
class Database:
    def query(self, sql: str):
        return self.conn.execute(sql)

ASCII Call Graph

GET /api/patients/search | v routes.py :: get_patient_endpoint(query) | v services.py :: PatientService.search(query) | v repositories.py :: PatientRepo.execute(query) | v db.py :: Database.query(sql) [SINK: SQL INJECTION]

Call Graph Data Structure

Internally, this is stored as an adjacency list / edge list:

# Edge list representation
edges = [
    ("routes::get_patient_endpoint", "services::PatientService.search"),
    ("services::PatientService.search", "repositories::PatientRepo.execute"),
    ("repositories::PatientRepo.execute", "db::Database.query"),
]

# Adjacency list representation
adjacency = {
    "routes::get_patient_endpoint": ["services::PatientService.search"],
    "services::PatientService.search": ["repositories::PatientRepo.execute"],
    "repositories::PatientRepo.execute": ["db::Database.query"],
    "db::Database.query": [],
}

# Neo4j storage (Cypher)
CREATE (a:Method {name: "get_patient_endpoint", file: "routes.py", repo: "patient-api"})
CREATE (b:Method {name: "PatientService.search", file: "services.py", repo: "patient-api"})
CREATE (a)-[:CALLS_DIRECTLY {line: 5}]->(b)

Blast Radius Computation

When a vulnerability is found at a specific method (the sink), BlanketAudit computes its blast radius by reverse-traversing the call graph to find every entry point that can reach it. Here is the step-by-step process:

1 Identify the sink. The vulnerable method is db.py::Database.query(), which executes an unsanitized SQL string.

2 Reverse BFS. Starting from Database.query(), follow incoming edges (callers) backwards through the graph:

Database.query() ← SINK (start here) ^ | PatientRepo.execute() ← depth 1 ^ | PatientService.search() ← depth 2 ^ ^ | | GET /patients/search POST /patients/bulk ← depth 3 (entry points) ^ | GET /reports/patient-list ← depth 4 (cross-repo entry)

3 Count entry points. Every node in the reverse BFS that is marked as an entry point (has an HTTP route / queue listener / cron trigger) contributes to the count.

4 Count repos. Check the repo field on each traversed node. If the BFS crosses into a different repository (via a cross-repo edge), increment repos_affected.

5 Estimate daily calls. Sum the estimated request rates of each entry point. This is derived from HTTP access logs (if available) or heuristic estimates based on route type.

BlastRadius Output

BlastRadius(
    entry_points=3,           # 3 HTTP endpoints reach this sink
    repos_affected=2,         # patient-api + reporting-service
    daily_calls="~5,000",      # Combined traffic to these endpoints
    affected_users="All patients with search access"
)
The blast radius is attached to every finding in the report and is used as a score multiplier. A SQL injection reachable from 1 internal-only endpoint scores much lower than the same vulnerability reachable from 8 public-facing endpoints across 3 repos.

Call Chain Tracing

A call chain is the specific path from an entry point down to the vulnerability. It is built by selecting the most relevant forward path from each entry point to the sink. Each step is a CallChainStep with a step_type that determines how it is rendered in the report: 

[
    CallChainStep(
        method="GET /api/patients/search",
        step_type="entry",            # HTTP endpoint (green in report)
        repo="patient-api"
    ),
    CallChainStep(
        method="PatientService.search(query)",
        step_type="method",           # Internal method call (blue)
        repo="patient-api"
    ),
    CallChainStep(
        method="PatientRepo.execute(query)",
        step_type="taint",            # Tainted data flows through (orange)
        repo="patient-api"
    ),
    CallChainStep(
        method="db.execute(f'SELECT * FROM patients WHERE name={query}')",
        step_type="sink",             # Vulnerable sink (red in report)
        repo="patient-api"
    ),
]

Cross-Repo Matching

When scanning multiple repositories, BlanketAudit detects HTTP client calls in one repo that correspond to endpoint handlers in another repo. This creates cross_repo edges in the call graph, enabling blast radius analysis that spans service boundaries.

How It Works

1 Extract HTTP clients. Find all outbound HTTP calls: 

# In patient-api/services/claim_service.py
response = requests.post(
    "http://payment-engine/api/payments/charge",
    json={"amount": claim.total, "patient_id": claim.patient_id}
)

2 Extract HTTP handlers. Find all endpoint definitions: 

// In payment-engine/src/main/java/PaymentController.java
@PostMapping("/api/payments/charge")
public ResponseEntity<PaymentResult> charge(@RequestBody ChargeRequest req) {
    return paymentService.processCharge(req);
}

3 Normalize and match paths. Path parameters are normalized to a canonical form for matching:

Framework SyntaxExampleNormalized
FastAPI / Spring/api/patients/{id}/api/patients/{param}
Express.js/api/patients/:id/api/patients/{param}
Go (gorilla/mux)/api/patients/{id:[0-9]+}/api/patients/{param}
Client call/api/patients/123/api/patients/{param}

4 Create cross-repo edges. When a client call's normalized path + HTTP method matches a handler's normalized path + HTTP method, a CrossRepoEdge is created: 

CrossRepoEdge(
    from_method="patient-api::ClaimService.submit_claim()",
    to_method="payment-engine::PaymentController.charge()",
    via="POST /api/payments/charge"
)

These edges allow the blast radius of a vulnerability in payment-engine to include entry points in patient-api, and vice versa. The call graph becomes a unified multi-repo graph.

How Search Works

When an agent needs to find relevant information, it embeds the query and performs an approximate nearest neighbor (ANN) search: 

# Compliance agent: find clauses relevant to "logging patient SSN"
query = "logging personally identifiable health information in plaintext"
query_embedding = get_embeddings().embed_query(query)

results = milvus_client.search(
    collection_name="compliance_clauses",
    data=[query_embedding],
    limit=5,
    output_fields=["framework", "clause", "title", "full_text"]
)

# Returns (ranked by cosine similarity):
# 1. HIPAA §164.312(a)(1) — Access Control (0.92)
# 2. HIPAA §164.530(c) — Administrative Safeguards (0.87)
# 3. SOC2 CC6.1 — Logical Access Controls (0.84)
# 4. GDPR Art. 32 — Security of Processing (0.81)
# 5. PCI-DSS Req 3.4 — Render PAN Unreadable (0.78)

The retrieved clauses are injected into the agent's prompt as context, enabling the LLM to make accurate compliance mappings grounded in the actual regulatory text rather than relying on its training data alone.
