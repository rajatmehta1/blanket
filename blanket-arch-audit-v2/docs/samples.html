Section 2 — Executive Summary

EXECUTIVE SUMMARYSection 2 of 9

The MedPay platform presents critical security and compliance deficiencies that require immediate remediation. Seven critical-severity findings were identified, including plaintext PHI logging to external monitoring services, SQL injection vulnerabilities in patient search endpoints, and unencrypted payment card data in transit between the claims processor and payment engine. The platform's current architecture allows protected health information to flow through 8 API entry points without adequate access controls, audit logging, or encryption at rest — placing the organization in direct violation of HIPAA §164.312(a)(1) and PCI-DSS Requirement 3.4.

Cross-repository analysis revealed 14 service-to-service HTTP calls with no mutual TLS or authentication token validation, creating a lateral movement path that could allow an attacker who compromises any single service to access patient records, payment data, and insurance claims across all three repositories. The call graph analysis identified 3 circular dependencies and 47 dead methods (1,200 lines) contributing to maintenance burden. The combined HIPAA compliance score of 18/100 indicates the platform is not audit-ready and faces potential penalties of $50,000–$1,900,000 per violation category under the HITECH Act.

Immediate Actions Required
  1. Stop logging PHI to Datadog. Mask all patient SSN, DOB, and diagnosis fields in log statements within 24 hours. 3 files affected.
  2. Parameterize all SQL queries. Replace f-string SQL construction in patient_service.py and claims_repo.py with parameterized queries. 5 injection points identified.
  3. Encrypt card data in transit. Enable mTLS between claims-processor and payment-engine. Card numbers are currently sent as plaintext JSON over internal HTTP.
  4. Add authentication to internal APIs. All 14 cross-repo HTTP calls lack bearer token or mTLS validation. Implement service-to-service auth using JWT or mTLS certificates.

Section 4 — Critical Findings

Below is finding BLK-001 rendered as it appears in the report, with every field populated:

CRITICAL BLK-001 · SEC-003 PHI Logged in Plaintext to External Monitoring
patient-api / services/patient_service.py : lines 42–44
Code
41 def process_claim(self, patient: Patient, claim: Claim): 42 logger.debug(f"Processing patient: {patient.ssn}, DOB: {patient.dob}") 43 logger.info(f"Claim diagnosis: {claim.diagnosis_code} for {patient.full_name}") 44 result = self.claims_repo.submit(patient, claim)
AI Explanation

This code logs protected health information (PHI) — including Social Security numbers, dates of birth, diagnosis codes, and patient names — directly into application logs using Python's standard logging library. These logs are shipped to Datadog via the configured log handler, meaning PHI leaves the application boundary and is stored in a third-party SaaS platform without a Business Associate Agreement (BAA) covering log data specifically.

Under HIPAA §164.312(a)(1), covered entities must implement technical safeguards to control access to electronic PHI. Logging PHI in plaintext to an external service violates this requirement because: (1) the data is not encrypted at rest in the logging platform, (2) access controls on log viewers are broader than the minimum necessary standard, and (3) there is no audit trail of who accessed these logs. The HITECH Act establishes penalties of $50,000 per violation up to $1.9M per violation category annually.

QuickLend — Personal Loan Origination Platform · Fintech

2 repos (loan-api Go, underwriting-engine Python), PCI-DSS + SOC2 frameworks. 4 critical, 11 high, 22 medium findings.

4 Critical 11 High 22 Medium 18 Low

Top Findings

CRITICAL Plaintext Card Storage

Credit card numbers stored as plaintext VARCHAR in PostgreSQL. PCI-DSS Req 3.4 requires rendering PAN unreadable. Estimated exposure: $100K–$500K per breach.

CRITICAL float64 Financial Math

Loan interest calculations use Go float64, causing rounding errors of up to $0.03 per calculation. At 50K loans/month, cumulative error reaches $18K/year. Use shopspring/decimal.

CRITICAL Circular Dependencies

5-node circular dependency: LoanService → CreditCheck → RiskEngine → PricingService → LoanService. Creates deployment ordering issues and makes testing impossible in isolation.

HIGH Missing Rate Limiting

The /api/loans/apply endpoint accepts unlimited requests. An attacker could submit thousands of loan applications to perform credit bureau enumeration.

Top Findings

CRITICAL Multi-Tenant Data Leak

API queries filter by user_id but not tenant_id. A user in Tenant A can access documents belonging to Tenant B by guessing document UUIDs. SOC2 CC6.1 violation.

CRITICAL Stored XSS via dangerouslySetInnerHTML

User-supplied markdown is rendered with dangerouslySetInnerHTML without sanitization. An attacker can inject <script> tags that execute in other users' browsers.

HIGH No GDPR Data Export

No endpoint exists for GDPR Article 20 data portability. Users cannot export their data in a machine-readable format. Must implement GET /api/users/{id}/export.

HIGH Worker Queue Poisoning

The background worker deserializes Redis queue messages with pickle.loads() without validation. A compromised Redis instance enables remote code execution.
